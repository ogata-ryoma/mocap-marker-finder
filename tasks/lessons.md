# Lessons

## 見えない機能の検証は「最悪ケースの環境」を合成して自動判定する

カメラや LED のようにハードウェアに依存する機能は、開発機では目視できないため「実機で試すまで分からない」と諦めがちになる。しかし**判定対象を機能そのものではなく、機能が前提にしている物理条件に置き換える**と、開発機でも合否が出せる。

今回は torch（LED）の点滅で環境光を打ち消す方式を、canvas で合成した偽カメラで検証した。ポイントは「動く絵を映す」ことではなく、**設計が狙っている最悪ケースをそのまま数値で再現する**こと。

- 背景 60、マーカー 72（明るい部屋で反射材がほとんど目立たない状態）
- torch ON で背景 68、マーカー 255（再帰反射だけが強く返る）

この条件で通常モードは 0 個、差分モードは 3 個を検出した。つまり「差分方式に意味があるか」という設計の核心を、実機を触る前に判定できた。合成条件を設計書のリスク記述からそのまま起こすのがコツ。

**汎用化**: 実機検証は「本当に動くか」の最終確認に取っておき、「設計が正しいか」は合成した最悪ケースで先に潰す。順序を逆にすると、実機で失敗したときに原因が設計なのか実装なのか端末なのか切り分けられなくなる。

## ブラウザ API のスタブは「失敗の仕方」まで再現する必要がある

Chromium の canvas captureStream トラックに `applyConstraints({ advanced: [{ torch: true }] })` を投げると、黙って無視されるのではなく `UnknownError: setPhotoOptions failed` を投げた。「対応していない制約は無視される」という一般論を前提に検証手順を組んでいると、ここで詰まる。

結果的にこれは怪我の功名で、非対応端末の判定経路（点灯に失敗 → 非対応画面 → カメラ停止）が意図せず実地で確認できた。一方で正常系の検証には、トラックの `applyConstraints` を差し替えて成功を模す必要があった。

**汎用化**: API をスタブするとき、成功パスだけ作ると片手落ちになる。実環境が「どう失敗するか」を先に観測し、成功用と失敗用の両方のスタブを用意する。失敗の形は推測せず、必ず 1 回実物を叩いて確かめる。

## 大きなコード片はシェルの heredoc で書かない

200 行規模の JavaScript を `cat > file <<'EOF'` で書こうとして `unexpected EOF while looking for matching '` で失敗し、ファイルが 0 バイトも作られなかった。同じ書き方で数十行のファイルは 6 回とも成功していたので、差は分量だけ。原因は特定していない。

**汎用化**: 引用符・バッククォート・`$` が密に混ざる長文は、シェル経由ではなくファイル書き込み専用の手段で書く。失敗が「部分的に壊れたファイル」ではなく「何も起きない」形で出るとは限らないので、書いた直後に `node --check` などの構文検査と文字コード確認（`file`）を通す癖をつける。

## Windows で日本語を含むファイルを書くときは UTF-8 を明示的に確認する

PowerShell の `Set-Content` / `Add-Content` は既定でシステム ANSI コードページを使うため、日本語を含むファイルが文字化けした状態で commit される事故が起きやすい。しかも git は文句を言わないので、ブラウザで開くまで気付かない。

**汎用化**: 日本語を含むファイルを新規作成したら、その場で `file <name>` を通して `UTF-8 text` を確認する。最初の 1 ファイルで確認しておけば、以降は同じ手段を使う限り安全。
